## 一、项目背景

这是一个 **GitHub 个人 Fork 项目**：

- **上游仓库**：`powerfullz/override-rules`（Mihomo/Clash 代理分流覆写规则，TypeScript 编写）
- **我们的 Fork**：`LeiD215/override-rules`
- **用途**：为 Mihomo/Sub-Store 生成代理分流配置（一个 JS 覆写脚本 `convert.min.js` + 若干静态 YAML 覆写）

### 技术形态（关键）

| 项 | 说明 |
|----|------|
| 源码 | `src/*.ts`（`main.ts` 入口、`proxy_groups.ts` 代理组、`rules.ts` 规则、`rule_providers.ts` 规则源、`constants.ts` 常量、`types.ts`） |
| 构建产物 | `convert.js` / `convert.min.js` / `yamls/`（由 esbuild + generator 生成，**不入 git**） |
| 规则数据 | `ruleset/*.list`（纯文本，一行一条） |
| 发布机制 | GitHub Actions `release.yaml`：从 git tag `src-vX.Y.Z` 切出版本号 → 构建产物 → 推送到 `dist` 分支 + 建 GitHub Release |

### 一个对"同步"至关重要的设计特点

- **`ruleset/*.list`（规则数据文件）是通过 rule-provider 以 `@main` 动态分支拉取的**（如 `https://cdn.jsdelivr.net/gh/LeiD215/override-rules@main/ruleset/MustDirect.list`），**不依赖版本号**。改了 `main` 分支上的 `.list`，客户端下一次拉取即生效，**不需要发版**。
- **`src/*.ts` 源码改动才需要发版**（编译进 `convert.min.js`，通过 tag/release 流程发布到 `dist`）。

## 三、核心问题：如何与上游保持同步

### 现状

- 我们 fork 时基线是上游 **v2.5.5**。此后**我们做了 50 个 commit，上游自己也前进了 11 个 commit（到 v2.7.0）**。
- **我们从 v2.5.5 之后从未同步过上游**。上游 v2.7.0 相比 v2.5.5 的关键改动：
  - 移除 SSH 代理组、移除"低倍率节点"分组
  - **新增 Tailscale 支持**（节点解析、分组、TUN 路由排除）
  - 重写 `src/rules.ts`（改成 `baseRules` 数组写法）
  - 大改 `src/dns.ts`（重写 fake-ip-filter 列表）

### 当前同步方式（痛点）

项目 SOP 目前只写了最简单直接的办法：

```
git fetch upstream
git merge upstream/main
```

但因为我们改的 `src/proxy_groups.ts` / `src/rules.ts` / `src/main.ts` / `src/constants.ts` **恰好也是上游 v2.7.0 改的文件**，所以 merge 会产生**多处冲突，需要人工逐个文件取舍**（"保我们的自定义" vs "收上游新功能"）。

我们已经尝试过一次 merge，**冲突文件有 7 个**：
`CHANGELOG.md`、`package-lock.json`、`package.json`、`src/main.ts`、`src/node_parser.ts`、`src/proxy_groups.ts`、`src/rules.ts`。

（规则数据、`_fork/` 记录区、`icons/` 等**无冲突**，上游没动。）

### 我们认为的"治本方向"

初步思路是：**不要用 merge 把"我们的自定义"和"上游演进"混在一起**，而是——

1. 把我们相对上游基线 v2.5.5 的全部自定义，**精确梳理成一份"补丁/清单"**；
2. 上游发布新版本时，**以新版本为干净基底，把我们这些补丁一项项"重放"回去**（类似 rebase / cherry-pick）；
3. 每个补丁能否干净应用、会不会被上游改动影响，都能**清晰可见**。

这样比"一次性大 merge + 人工解一堆冲突"更可控、可审计、可长期维护。

## 四、我们已列出的候选方案（从轻到重）

| 方案 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **A. 固化同步 SOP（最轻）** | 把"先梳理自定义清单 → fetch 上游 → 以新版本为底重放补丁 → 验证 → 发布"写成一份可执行手册，存进 `_fork/` | 立刻可用，记录即成索引 | 仍是半手工 |
| **B. 建 custom-patches 补丁目录** | 把我们的自定义导出成独立 `.diff`/`.patch` 文件存进仓库，升级时用脚本自动重放 + 报告冲突点 | 半自动，冲突可视化 | 需维护补丁与源码同步 |
| **C. 长线解耦重构（重）** | 把自定义逻辑从上游源码中彻底解耦（如抽成独立模块 / 独立 provider / 通过参数或配置文件驱动），使 `src/` 主源码尽量贴近上游 | 治本，未来 merge 几乎零冲突 | 需一次较大重构，风险与工作量高 |

## 五、想请您评估的具体问题

1. **最推荐哪条路线？** A / B / C 或它们的组合？还有没有我们没想到的更好方案？（比如：Git submodule / subtree、`git merge` 配 `ours`/`theirs` 策略、用补丁管理办法等）

2. **这次的 v2.5.5 → v2.7.0 同步，最优的具体执行步骤是什么？**
   考虑到我们希望"保住全部自定义 + 吸收上游有价值的改动（尤其 Tailscale）"，是先用 `git diff` 把自定义清单导出，还是直接建一个基于 v2.7.0 的分支逐项 cherry-pick？合并冲突时如何判断保留哪边？

3. **对于"rule-provider 用 `@main` 动态拉取 .list"这种设计**，有什么要注意的？它虽然让我们改规则数据不用发版，但会不会引入别的风险（如版本不可复现、CDN 缓存）？是否值得为 `.list` 也引入版本化？

4. **长期维护**上，个人 Fork 跟随上游最可持续的最佳实践是什么？是否应该尽量"少改上游源码、多通过增加独立文件/provider 来扩展"，从而让 fork 的上游部分永远能和上游保持同步？
