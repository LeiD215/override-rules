B（`custom-patches` 补丁目录）看起来是"半自动"，实际上是把 git 已经做的事再手工做一遍：补丁文件和源码是两份真相，你每改一次 `src/*.ts` 就得记得同步补丁，忘了就静默失效；而且 `.patch` 依赖上下文行，上游一重构（比如这次 `rules.ts` 改成 `baseRules` 数组写法）补丁照样烂掉，只是把"merge 冲突"换成了更难读的"patch hunk failed"。发行版打包（quilt/dpkg）用补丁栈，是因为它们**没法**为每个上游版本维护 git 分支——你有 git，没必要退回去。

```ts
return [...baseGroups, ...forkGroups(params)];
```

`rules.ts` 因为有顺序要求，留三个点：`forkPrependRules`（MustDirect/MustProxy/MustReject 强制链）、一个中段插入点（MyDirectCDN / Adobe / Autodesk 优先级）、`forkAppendRules`。`constants.ts`、`main.ts` 各一行。

| 类别 | 做法 |
|---|---|
| 纯新增文件（`_fork/`、`ruleset/*.list`、`icons/`、`scripts/`） | `git checkout main -- _fork ruleset icons scripts`，零风险 |

- 上游改的是**结构/写法**（数组化、函数签名、类型定义）→ **一律取上游**。不为保留旧写法抵抗上游重构。
- 我们要保的是**语义**（有哪些组、哪些 provider、规则的先后顺序）→ **一律保我们的**，但用上游的新写法重新表达。
- 上游**删除**的东西（SSH 组、低倍率分组）→ **默认接受删除**，但先 `grep` 我们的 rules/groups/constants 有没有引用这些组名常量，有引用会直接编译失败或产出悬空策略组。
- 上游**新增**的东西（Tailscale）→ **默认全收**，收完再单独决策要不要为它加自定义（比如 Tailscale 的 100.64.0.0/10 要不要进 MustDirect、TUN 排除是否和你现有直连清单打架）。
- 生成物/锁文件 → **不解冲突，重新生成**。

**验证是这次同步的关键闸门**，不能只跑 `tsc --noEmit` + `npm run build`：

```bash

```

再用真实订阅数据分别调用新旧产物的 `main(config)`，把两份输出 YAML 做结构 diff。**验收标准**：差异应当恰好等于「上游的 Tailscale 新增 + SSH/低倍率组移除 + dns 重写」加「我们的自定义全部在位且顺序正确」，**不能有第三类差异**。出现第三类差异就是重放漏了东西。

最后合回 main，用这个手法保住上游祖先关系（关键——否则下次同步又要从 v2.5.5 开始 diff）：

```bash
git checkout sync/upstream-v2.7.0

git merge sync/upstream-v2.7.0  # fast-forward
```

## 关于 `@main` 动态拉取 `.list`

这个设计的便利是真的，但有四个风险，其中两个你们大概率低估了：

1. **jsDelivr 对分支引用有缓存，"下次拉取即生效"很可能不成立。** `@main` 这类可变引用在 jsDelivr 上有以小时计的 CDN 缓存（`@tag`/`@commit` 才是不可变永久缓存）。你们文档里那句假设值得实测一次——改一条 MustDirect 然后掐表看多久生效。如果确实有数小时延迟，SOP 里必须写明，否则以后排查"规则改了没生效"会浪费大量时间。

2. **可复现性断裂**（我认为这是最实质的问题）。`convert.min.js` 是版本化的，它引用的规则数据是活的。同一个 v2.5.16 在不同时间点产生的实际分流行为不同，出故障时没法回答"当时的规则到底是什么"。

3. **可用性**：jsDelivr 在大陆网络下不稳定。如果 `MustDirect.list` 拉取失败，mihomo 的行为取决于 provider 的 fallback 配置——最坏情况是"必须直连"的东西被代理出去。**建议把真正救命的几条（NAS 管理口、内网段、你自己的 VPS）用内联 RULE 或本地 provider 再兜一份**，不要只依赖远程拉取。

4. 分支被误 push / 账号被盗时没有版本门槛，改动即时下发到所有客户端。

**建议：不要全面版本化，改成"保留 @main + 增加可复现快照"。** 在 `release.yaml` 里加一步，发版时把当时的 `ruleset/` 目录打包进 GitHub Release assets（或同步一份到 `dist` 分支）。日常使用路径完全不变，零额外成本，但每个版本从此都有"当时规则数据"的不可变快照，可查可回滚。

再细一层，两类 `.list` 其实诉求不同：`MustDirect/MustProxy/MustReject` 是应急型，需要即时生效，保持 `@main`；`Autodesk.list`（脚本生成）、`MyDirectCDN.list` 变化不频繁，完全可以跟版本走。

```text
upstream providers
    +
fork providers
```

或者：

```text
build upstream rules
→ apply fork rule policy
```

最后你们真正碰上游代码的位置可能从几十处降低到：

> **几个 import + 几个调用点。**

这才是我认为值得追求的 C。

不是“绝对零修改上游”。

而是：

> **把 fork delta 做小、集中、可识别。**

# 九、Submodule / subtree / ours-theirs，我都不推荐

### Git submodule

不适合。

Submodule 擅长的是：

> “A 项目依赖 B 项目，但不修改 B。”

而你们的问题恰好是：

> “我要修改上游内部逻辑。”

所以解决不了核心问题。

### Git subtree

同样只是改变“代码怎么放进来”，并没有解决你们和 upstream 修改相同代码的问题。

### `merge -X ours/theirs`

风险更大。

例如 `rules.ts`：

* upstream Tailscale 要留；
* fork MustDirect 要留；
* upstream SSH 删除要留；
* fork Adobe 优先级也要留。

根本不存在一个：

> “这个文件选 ours”

或：

> “这个文件选 theirs”

能正确解决。

# 十、可以启用 Git `rerere`

这是我建议加入 SOP 的一个小工具：

```bash
git config rerere.enabled true
```

Git 会记住以前你是怎么解决相同冲突的。

以后 upstream 又在相邻位置改动时，有机会自动复用上次的解决结果。

但要注意：

# 十一、`ruleset/*.list @main`：我认为可以保留，但必须补治理

你们这个设计并不是错误。

而且对：

* MustDirect
* MustProxy
* MustReject

这种运营型规则来说非常实用。

你们当前代码确实把这些 provider 指向 Fork `@main`，而 Mihomo 本身又会按照 `interval` 周期重新抓取。你们的 MustDirect/MustProxy 等目前是 86400 秒更新周期。([GitHub][4])

但它确实带来两个风险。

### 1. 不可完全复现

今天：

```text
convert.min.js v2.5.16
+
MustDirect@main
```

和一个月后的：

```text
convert.min.js v2.5.16
+
MustDirect@main
```

可能产生不同结果。

所以：

> **JS 版本固定 ≠ 完整运行配置固定。**

这个必须在文档里明确。

### 2. CDN 缓存

这个问题是真实存在的。

jsDelivr 官方目前明确说明，类似 `latest`/alias 这种非固定版本 URL 如果不 purge，用户可能最长等待 **7 天** 才得到更新。([jsDelivr][5])

你们现在 release workflow 已经专门 purge `convert.min.js` 的 jsDelivr 缓存。([GitHub][6])

**但是规则文件的 `@main` 更新也应该有同样的 purge。**

这反而是我看完仓库后认为应该补的一项。

建议增加一个很小的 Action：

```text
ruleset/*.list changed
        ↓
自动 purge 对应 jsDelivr URL
        ↓
fetch 验证
```

这个投入很小，收益很明显。

# 十二、我不建议为了“可复现”就完全取消 `@main`

那会牺牲你们现在很有价值的能力：

> **改规则无需重新发布 JS。**

所以我推荐双层思想：

### Live channel

```text
@main/ruleset/*.list
```

用于日常真正运行。

优点：

> 快速改策略。

### Snapshot / rollback

Git commit/tag 本身保存每次规则状态。

```text
ruleset revision
commit SHA
时间
原因
```

必要时能马上 pin 到某个 commit SHA 或回滚 main。

也就是说：

> **运行使用 moving channel，审计和恢复使用 immutable commit。**

我认为比强迫所有规则文件跟 JS 一起发版更适合你们。

| ------------------------------- | --------------------------------------------- |
| 当前 `merge upstream/main`        | **停止作为默认同步方式**                                |
| A 同步 SOP                        | **采用**                                        |
| B `.patch` 目录                   | **不作为长期真相源**                                  |
| D Git custom commit stack       | **作为核心机制**                                    |
| C 完全解耦                          | **不立即实施**                                     |
| C-lite 减少 upstream touch points | **逐步实施**                                      |
| submodule/subtree               | **不采用**                                       |
| ours/theirs 自动合并                | **不采用**                                       |

| upstream base 元数据               | **强烈建议增加**                                    |

### 一、 路线评估：最推荐的方案组合

**推荐结论：短期采用「Git Rebase 重放策略 + SOP 固化（A的升级版）」，长期全面转向「长线解耦重构（C）」。强烈不建议方案 B。**

* **强烈不推荐方案 B（custom-patches）：** 代码补丁（`.patch` / `.diff`）高度依赖上下文行号。上游对 `src/rules.ts` 等文件进行了重写（如改为 `baseRules` 数组），补丁会瞬间失效且无法自动应用，维护成本极高。
* **最佳中间态（您没想到的方案）：Git Rebase。** 您的初步思路“以新版本为干净基底，把我们这些补丁一项项重放回去”，这在 Git 中的原生实现就是 `git rebase`。与 `merge`（交织历史）不同，`rebase` 会把上游的最新代码作为地基，将您的自定义 commit 重新“长”在上面，完美契合您的治本思路。
* **长治久安（方案 C）：** 只要您的自定义代码和上游代码在同一个文件（如 `src/rules.ts`）里物理混杂，每次上游重构您都会痛。必须通过工程化手段将其物理隔离。

### 二、 本次 v2.5.5 → v2.7.0 的最优执行步骤

直接 Rebase 50 个 commit 可能会导致您在同一个文件上反复解决 50 次冲突。为了“保住全部自定义 + 吸收 Tailscale 等新特性”，推荐以下「压缩后变基（Squash & Rebase）」的打法：

**1. 准备与备份**

```bash
git fetch upstream
# 停留在您的 main 分支，先建一个备份，以防万一
git branch main-backup-2.5.16

```

**2. 浓缩您的 50 个自定义 Commit**
为了避免在 `rebase` 时解决 50 次碎片化冲突，建议先将您的 50 个改动合并为几个核心 Commit（例如：`feat: 增加 AI 与设计软件规则`、`chore: 增加 CI 与 fork 记录`）。
*可以利用交互式变基：*

```bash
git rebase -i ca977f0 # ca977f0 是上游 v2.5.5 的 commit

```

*在弹出的编辑器中，将除了第一个 commit 之外的所有 `pick` 改为 `squash`，合并为一个或几个干净的“自定义全集 Commit”。*

**3. 向 v2.7.0 变基（重放补丁）**

```bash
git rebase upstream/main

```

**4. 冲突解决策略（合并法则）**
由于上游重写了 `rules.ts` 和 `dns.ts`，冲突必然发生。此时的解决原则是 **“上游架构为主，注入自定义为辅”**：

* **CHANGELOG.md / package.json：** 直接使用上游（theirs）的，然后再手动补上您的版本号注入逻辑。
* **src/rules.ts：** **接受上游的全部修改**（包含 Tailscale 路由排除和新的 `baseRules` 数组写法）。然后，将您的 `MustDirect/MustProxy/Adobe` 等规则，按照最新的数组语法，手动追加或插入到该文件合适的位置。

```bash
git push origin main --force # 由于重写了历史，需要 force push

```

### 三、 关于 `@main` 动态拉取 `.list` 的风险评估

您当前的 `rule-provider` 设计十分轻量，但确实存在两个需要注意的风险点，建议进行轻度改造：

1. **CDN 缓存刺客（最大的直接风险）：**
`[https://cdn.jsdelivr.net/gh/LeiD215/override-rules@main/](https://cdn.jsdelivr.net/gh/LeiD215/override-rules@main/)...` 这种写法，jsDelivr 默认有 **24 小时左右的缓存**。您在 `main` 分支更新了 `.list`，客户端拉取到的可能还是昨天的数据。
* **缓解方案：** 要么在 Mihomo/Clash 配置的 url 后面拼接无意义的时间戳参数打穿缓存（如 `?t=20260821`），要么改用 `raw.githubusercontent.com`（缓存时间较短，通常 5 分钟），但这取决于客户端的网络连通性。


2. **版本不可复现（“时光机”失效）：**
如果未来 `.list` 里的规则格式需要配合 `convert.min.js` 的新逻辑，旧版本的 JS 读取新版本的 `.list` 可能会崩溃。
* **建议：** 如果 `.list` 只是纯粹的域名/IP 文本增删，继续使用动态拉取没问题，**不值得为了纯文本数据走发版流程**；但如果涉及语法或结构的改变（例如新增了特定标签），则必须新建文件（如 `MustDirect-v2.list`）或跟随 Release 版本号固化拉取地址（`@v2.X.X`）。

### 四、 长期维护最佳实践：解耦重构（方案 C 的落地）

为了让以后的同步像喝水一样简单，您的核心目标是：**实现对上游核心文件的“零侵入”或“单行侵入”。**

以 `src/rules.ts` 为例，上游改成了 `baseRules` 数组，您应该这样做：

**1. 建立自定义模块目录**
新建 `src/custom/` 目录（例如 `src/custom/my_rules.ts`），在这个文件里用上游相同的类型定义您的规则：

```typescript
// src/custom/my_rules.ts
import { Rule } from '../types';
export const myCustomRules: Rule[] = [
    // 您的 MustDirect, Adobe, Autodesk 等逻辑
];

```

**2. 单行侵入上游文件**
在合并后的上游 `src/rules.ts` 中，只做最少量的修改：

```typescript
// src/rules.ts (上游文件)
import { myCustomRules } from './custom/my_rules'; // 侵入点 1

export const baseRules = [
    // ... 上游原有的几十行规则 ...
    ...myCustomRules, // 侵入点 2：将您的规则解构注入
];

```

**为什么这样做最好？**
下次上游无论怎么大改 `src/rules.ts` 内部的规则顺序或增删，只要不改变抛出的数组结构，Git 合并时极大概率会自动成功，或者只需要您把 `...myCustomRules` 这行代码重新贴一次即可。这才是个人 Fork 长期跟随上游的终极形态。

# Fork 项目上游同步方案评估与执行指南
## 一、路线推荐：短期结构化重放 + 长期最小化解耦
结合你的项目规模、自定义特点和长期维护需求，**不建议单选 A/B/C，推荐采用「以 Git 原生 rebase 能力为核心，替代人工补丁维护；本次同步顺便完成轻量化解耦；沉淀 SOP 兜底」的组合路线**，优先级从高到低如下：

### 1. 核心主线：Git 分支+原子化 commit+rebase，替代 B 方案的补丁目录
你考虑的 B 方案（维护 .patch 文件）会带来额外的补丁与源码同步成本，且容易出现补丁过时、上下文不匹配的问题。Git 本身就是最可靠的补丁管理工具：
- 维护一个纯上游跟踪分支，永远不写入自定义代码，仅与上游 tag/main 同步；
- 所有自定义功能拆分为**原子化、语义化的独立 commit**，基于上游发布 tag 做 rebase 重放，冲突会精准定位到对应功能的 commit，无需额外维护补丁文件；
- 开启 `git rerere` 自动记录冲突解决方案，后续同步遇到相同冲突会自动复用解决逻辑。

### 2. 本次同步顺便落地：轻量化解耦（C 方案的低成本落地，非大规模重构）
你不需要做重度重构，只需要遵循「**能新增文件绝不修改上游源码**」的原则，把现有自定义逻辑从上游文件中抽离到独立的 `src/custom/` 目录，仅在入口文件保留极少的注册代码：
- 自定义规则、代理组、provider、常量、类型扩展全部放在 `src/custom/` 下独立维护；
- 仅修改 `src/main.ts` 不超过 5 行代码，完成自定义配置与上游生成结果的合并；
- 不得不修改上游源码的场景，用 `// [CUSTOM-START]/[CUSTOM-END]` 标记边界，未来同步直接搜索标记即可快速定位。
> 该重构只是代码挪移，没有新业务逻辑，工作量小、风险极低，完成后未来上游同步 90% 以上的场景不会有冲突。

### 3. 兜底：A 方案 SOP 文档化
把同步流程、冲突处理原则、自定义清单沉淀到 `_fork/sync/` 目录下，作为操作手册和故障回溯依据，不需要作为核心维护手段。

### 不推荐的方案
- **Git submodule/subtree**：仅适合依赖独立外部项目的场景，你是 Fork 后修改核心逻辑，用子模块会大幅增加复杂度，无收益；
- **整文件 merge 策略（ours/theirs）**：仅可用于完全放弃一方的文件（如上游 CHANGELOG），绝对不能用于源码文件，会直接丢失上游新功能或你的自定义逻辑；
- **长期靠手工 merge**：攒的版本越多，冲突越难解，且历史混乱不利于回溯。

## 三、冲突判断通用原则
遇到冲突时不要直接选一方，按以下优先级判断：
1. **上游通用核心逻辑**：以上游为准，包括 dns 解析、节点解析、核心规则框架、通用优化，不要为了你的自定义改动上游核心结构；
2. **个人专属扩展逻辑**：以你的自定义为准，包括专属规则、代理组、provider、版本信息，这类逻辑上游不存在，不会冲突；
3. **交叉适配场景**：手动把你的自定义逻辑嫁接到上游的新结构上（比如上游重写了 rules 数组，就把你的规则拼到新数组结构里，不要回退上游的重构）；
4. **完全无自定义的上游文件**：直接用上游版本，比如 CHANGELOG、dns.ts、你没改过的工具文件。

## 四、`@main` 动态拉取 ruleset 的风险与优化建议
这个设计非常适合规则频繁迭代的场景，收益（改规则无需发版、秒级生效）远大于成本，不需要全量版本化，但需要补几个措施规避风险：

### 现有风险
1. **版本不可复现**：Release 版本的 convert.min.js 与 main 分支规则解耦，问题排查时无法还原发布时的规则状态；
2. **CDN 缓存延迟**：jsDelivr 对分支资源默认缓存 12 小时，不同地区用户可能拿到不一致的规则版本；
3. **误操作影响范围大**：错误提交规则会直接同步给所有用户，无缓冲期。

### 优化措施（低成本，无需改架构）
1. **加规则提交校验**：pre-commit 钩子校验 .list 文件格式（无空行、无非法字符、域名/IP 合法性），避免坏规则提交；
2. **自动刷新 CDN 缓存**：在 CI 中加一步，当 `ruleset/` 目录有改动时，调用 jsDelivr Purge API 自动刷新对应文件，无需等缓存过期；
3. **可追溯标记**：构建时把当前 commit hash 注入到配置的 `x-override-rules` 头中，排查问题时可以快速对应到代码版本；
4. **规则改动记录**：每次改 ruleset 在 `_fork/CHANGELOG.md` 记录变更内容和 commit hash，方便回溯。

### 什么时候需要版本化？
如果后续用户量增长、对稳定性要求极高，可以采用双轨制：
- 开发/预览版：引用 `@main` 规则，享受实时更新；
- 正式 Release：构建时自动把规则引用替换为当前 commit hash（而非分支名），保证发布版本配置永久可复现。
个人使用阶段完全不需要做这步，动态拉取的效率更高。

## 五、Fork 长期维护最佳实践
1. **最小化上游改动原则**：这是最核心的长期维护原则——能加新文件就不改上游文件，能配置驱动就不改核心逻辑，不得不改的地方加 `[CUSTOM]` 标记，控制改动行数；
2. **固定分支模型**：
   - `upstream` 分支：纯上游镜像，永远只 fast-forward 上游代码，不提交任何自定义内容；
   - `main` 分支：你的自定义分支，永远基于上游的发布 tag 做 rebase，不要用 merge 拉取上游代码，保持线性历史；
3. **小步快跑同步**：上游发布小版本（如 v2.7.1）就同步一次，不要攒多个大版本再同步，版本跨度越小，冲突概率越低、解决成本越低；
4. **通用能力向上游贡献**：如果你的自定义功能是通用的（比如 Autodesk 规则、通用 bug 修复），尽量提 PR 贡献给上游，合并后你就可以删除对应自定义代码，从根源减少维护量；

## 3. `rule-provider` 用 `@main` 动态拉取 `.list` 的注意事项

```bash
git merge sync/v2.7.0
# 更新版本号
git tag src-v2.7.0
git push origin main --tags
```

### 冲突判断原则（"保留哪边"）

| 冲突类型 | 判断规则 |
|---------|---------|
| 上游删除了某功能（如 SSH 组、低倍率分组） | **接受上游的删除**，除非你的自定义依赖它 |
| 上游新增功能（如 Tailscale） | **接受上游新增**，不阻碍 |
| 上游重构写法（如 rules.ts 改 baseRules） | **采用上游新写法**，在新写法里重新实现你的自定义 |
| 你的自定义与上游新代码位置冲突 | 优先保证你的自定义逻辑正确，位置可以调整 |
| `CHANGELOG.md` | 直接用上游的，或清空让你自己的 git-cliff 重新生成 |

## 三、`@main` 动态拉取 `.list` 的风险评估

### 当前设计的优势（不要急着改）

- 规则数据热更新，不需要走发版流程
- 对个人项目来说，迭代速度极快
- 上游也是这么设计的，保持了一致性

### 实际风险矩阵

| 风险 | 严重程度 | 发生概率 | 缓解措施 |
|------|---------|---------|---------|
| jsdelivr CDN 缓存延迟（通常 12h） | 中 | 高 | 用 `@main` 而非版本号是对的；紧急时可换 `raw.githubusercontent.com` |
| 版本不可复现（无法回溯"3 天前的规则长什么样"） | 低 | 中 | git 本身就是版本控制，`git log -- ruleset/` 即可追溯 |
| `.list` 与 `convert.min.js` 不兼容 | **高** | 低 | 这是唯一真正危险的场景 |

### 唯一需要警惕的场景

如果你在 `src/rule_providers.ts` 中新增了一个 provider 名称（如 `MustDirect`），而 `.list` 文件已经上传到 main 分支引用了这个名称——但 `convert.min.js` 还没发版（还是旧版，不认识 `MustDirect`），客户端就会报错。

**建议**：在 `_fork/SOP` 中加一条规则：
> 新增 rule-provider 时，必须先发版 convert.min.js，再上传对应的 .list 文件。

### 是否需要为 .list 引入版本化？

**短期不需要**。理由：
- 你的 .list 是纯文本，git 已经提供了完整历史
- 引入版本号会增加维护负担，且上游没有这个机制
- 个人项目，回滚场景极少

**如果未来需要**，最轻量的做法是：在 `.list` 文件头部加注释行 `# version: 2026-08-21`，仅作标记，不参与逻辑。

## 一、总判断：A 是底座，B 不推荐单独做，C 的思路最对路

先说排序：

| 方案 | 我的态度 |

| **A. 固化 SOP** | ✅ 必做。是基础设施，不做后面任何方案都跑不转。 |
| **B. custom-patches 补丁目录** | ⚠️ **不推荐作为长期方案**。本质上是在"重新发明 git 的 rebase/cherry-pick"，且补丁要随源码改、随上游改而持续维护，长期是双倍工作量。短期可以当工具用（导出 diff 看清冲突），但别沉淀成仓库资产。 |
| **C. 长线解耦重构** | ✅ **方向最对**，但不必一步到位。这次先按"少改上游源码"的原则把这次同步做了，方案 C 的精神在过程中逐步落地。 |

**核心思路：把方案 C 当成"日常纪律"而不是"一次性大重构"**。具体说就是——

> **每个新需求在动笔前先问一句："这件事能不能不改任何已有文件，纯靠新增文件/新增 provider/新增组来实现？"** 能新增就新增，能后置就后置（构建期注入、运行时 import），实在要改上游文件就改得"小、准、原子"。

这样你的 fork 在结构上永远接近 upstream，merge 冲突会从"7 个文件"降到"1-2 个文件"，长期下来维护成本是单调下降的。

**为什么不推荐 B（patch 目录）？**
- patch 文件本身就是 git diff 的产物，它的"基线"也是漂移的——你这次导出的 patch，等下次上游一改，可能要重导
- patch 多了之后，谁也说不清"这块代码现在到底是 patch 状态还是合并后状态"
- git 自己的 `rebase --onto` / `cherry-pick` / `range-diff` 就是为这件事设计的，原生工具更好用

## 二、本次 v2.5.5 → v2.7.0 同步：具体执行步骤

**关键决策：用 "以 v2.7.0 为干净基底 + 定向 cherry-pick 我们的 50 个 commit"，而不是 "merge upstream/main"。**

理由很简单：
- 你上游只多了 11 个 commit，你这边多了 50 个。**把少的当基底、多的当增量，冲突点更可控**
- cherry-pick 一个 commit 是一个清晰的语义单元，冲突的"取舍粒度"天然是 commit 级；merge 是工作树级，冲突是文件级
- 每个 commit 都能单独验证（构建过、规则过）

### 推荐流程

```bash
# ===== 0. 备份 + 准备 =====
git checkout main
git tag archive/pre-sync-2.5.16   # 永远留个回得去的锚
git fetch upstream --tags
git fetch origin --tags

# ===== 1. 用 v2.7.0 干净基底开新分支 =====
git checkout -b sync/v2.7.0 upstream/main

# ===== 2. 一次性先把"零冲突 + 非 src 核心"的东西拿过来 =====
# 这些上游完全没动，可以直接 checkout 整片
git checkout archive/pre-sync-2.5.16 -- _fork/ icons/ ruleset/ scripts/ .husky/
git checkout archive/pre-sync-2.5.16 -- release.yaml package.json package-lock.json

# ⚠️ package.json 也要拿我们的（我们要对齐我们的依赖 + scripts.build.mjs 那条）
# 拿过来后看 diff：上游 v2.7.0 是不是也改了 dependencies？
#   - 如果只是 devDeps 多了 build 工具，合并不冲突就合并
#   - 如果 scripts 字段有冲突，保我们的（我们的是发布关键路径）

# ===== 3. 核心：把 src/ 的自定义一个个 cherry-pick 回来 =====
# 思路：不要 50 个 commit 一起 cherry-pick，先用 range-diff 看哪些 commit 真正涉及冲突文件

# 3.1 看哪些 commit 涉及冲突文件
git log --oneline archive/pre-sync-2.5.16 -- src/main.ts src/proxy_groups.ts src/rules.ts src/constants.ts src/types.ts src/node_parser.ts

# 3.2 把这些 commit 按主题分组（手动整理一下），然后分批 cherry-pick
# 例如：
git cherry-pick <commit-A>   # rule_providers.ts 的新增（上游 v2.7.0 应该也改过这个文件）
git cherry-pick <commit-B>   # proxy_groups.ts 新增 AI/ADOBE/AUTODESK 组
git cherry-pick <commit-C>   # rules.ts 新增强制规则链
git cherry-pick <commit-D>   # constants.ts 新增常量
git cherry-pick <commit-E>   # main.ts 版本注入
git cherry-pick <commit-F>   # types.ts 类型扩展

# 3.3 冲突时怎么取舍？决策表：

| 上游在这文件改了吗 | 我们要做什么 |
|---|---|
| 没改 | 无脑 `git checkout --ours`，合上 |
| 改了，但改的是"我们没碰的区域" | 通常能自动合并；不能就保留两边不同部分 |
| 改了，而且改的就是"我们要扩展的位置" | 手动解，逐段看：保留上游新逻辑 + 保留我们的新增项 |

# 一些会用到的小技巧：
#   - `git checkout --ours <file>`   ：冲突时只保我们的（用于"上游没改"的情况）
#   - `git checkout --theirs <file>` ：冲突时只保上游的（**慎用**，一般不用）
#   - `git log --oneline -p --follow <file>`：看这个文件的历史，知道哪段是谁加的

# ===== 4. 把我们独有但被 cherry-pick 漏掉的拿过来 =====
# 我们的 50 个 commit 里肯定有些是 _fork/ 文档/图标/规则数据，这些没冲突，前面 #2 已经处理
# 跑一遍 git status + git log，看看有没有遗漏

# ===== 5. 验证 =====
npm ci
npm run artifacts
# 把 dist 产物在本地 Mihomo/Sub-Store 跑一下
# 重点验证：
#   - AI/ADOBE/AUTODESK 代理组还在
#   - MustDirect/MustProxy/MustReject 规则链顺序对
#   - Tailscale 支持（上游 v2.7.0 新增的）也工作

# ===== 6. 发布 =====
git tag src-v2.7.0
git push origin sync/v2.7.0
# PR 走 review → merge 到 main → 触发 release.yaml
```

### 关于"合并冲突时保留哪边"

**永远不要无脑 `--ours` 或 `--theirs`**。这次的 7 个冲突文件每个都要单独判断：

- **CHANGELOG.md**：上游自动生成的，不要我们改的，让 git cliff 重新生成即可 → 直接用 theirs
- **package.json / package-lock.json**：要看具体 diff，一般是 devDeps 字段冲突，手动合 → 保留两边的依赖项
- **src/main.ts**：看你"版本元信息 x-override-rules"那个改动是几行的事，新版本如果 main.ts 整个结构没动，就手动把那几行原样插回去
- **src/node_parser.ts**：你们这版没改吧？冲突大概率是上游的；只要你们的自定义没在这个文件里，就 theirs
- **src/proxy_groups.ts / src/rules.ts**：这是大头，必须逐段看。建议用 `git log -p --follow` 把上游这 11 个 commit 怎么改这两个文件的先看一遍

## 三、关于 "rule-provider 用 @main 动态拉取 .list" 的设计

这个设计**对你们这种"频繁微调规则"的场景是合理的**，但确实有几条要注意的：

### 风险点

1. **不可复现性**：今天拉到 MustDirect.list 是 A 状态、明天发了新 .list 变成 B 状态，**用户客户端没有版本锚点**。出问题回滚只能"改回 .list"而不能"指回上个版本"
2. **CDN 缓存**：jsdelivr 对 `@main` 的缓存是分钟级但不是秒级，热修有时候"看上去没生效"
3. **跨分支不一致**：你在 main 上改了 .list 但没发 src-v2.7.0，客户端规则走 main 已经是新版，convert.min.js 还是 v2.5.16——这种"规则版本 ≠ 引擎版本"的不一致是隐性 bug 源

### 我的建议（**不要给 .list 加版本号**，但要做几件小事）

| 措施 | 怎么做 |
|---|---|
| **生产配置用 @tag，@main 留给开发/热修** | README 里写清楚"生产请用 @v2.7.0 这种 tag，不要用 @main" |
| **给 .list 同步加 release 钩子** | 在 release.yaml 里加一步：每次发 src-vX.Y.Z 时，把当前 main 上所有 ruleset/*.list 拷一份到 `dist` 分支的同路径，便于"快照回滚" |
| **.list 重大变更跟 src 发版同步** | "加一个新分组规则"这种"结构性"改动应该跟 src 一起发版，单纯"加几条域名"可以走 @main 热修 |
| **给 .list 加一个 `meta.list` 或 `_version.list`** | 在 ruleset/ 维护一个 `ruleset/_meta.list` 记录每份 .list 最近一次"实质性变更"的 commit sha，客户端或你自己排查问题时有据可查 |

**一句话：@main 这个机制保留，但只用于"非破坏性微调"；结构性变更走 release + 快照。**

## 四、长期维护的最佳实践（个人 Fork 跟随上游）

这是我觉得**最值得你沉淀进 _fork/ 的一份 ADR**，因为它是接下来几年你们每次同步都要用的纪律。

### 1. 核心原则：少改上游源码

每次想改一个已有文件前，自检三连：

> 1. 这件事能不能**纯新增**完成？（新文件 / 新 provider / 新组）
> 2. 如果非要改，能否**追加**而非**修改**？（在数组末尾 push / 在文件末尾追加 import）
> 3. 改的话，能否**只改这一处、保持其他区域逐字一致**？（让 git blame 干净，让 diff 一目了然）

### 2. commit 风格纪律

你们的 50 个 commit，按主题拆过没有？我看描述像是按"功能点"拆的（rule_providers 改一次、proxy_groups 改一次…）。**继续保持**。每改一个文件一个独立 commit，每个 commit 标题写"我们加了什么"而不是"修了什么 bug"——这样 cherry-pick 时一眼能看清意图。

### 3. 同步节奏

- **上游每次发版后 1 周内同步**，不要拖。拖久了 diff 越大冲突越难
- 用 **GitHub Action** 监听 upstream 的 release，**自动开一个 issue 提醒**（或发邮件），比 dependabot 简单
- 每次同步前在 _fork/STATUS.md 写一行"上次同步：v2.7.0 (date, upstream commit)"

### 4. 工具链建议

| 工具 | 用途 |
|---|---|
| `git worktree` | 同步时开一个独立 worktree，不污染主工作区 |
| `git range-diff` | 上游 v2.5.5..v2.7.0 跟我们 fork..HEAD 的对比，看我们的 commit 跟上游"对位"了没有 |
| `git rebase --onto` | 如果某段时间你们没发版但上游发了，可以用 --onto 把你们的 commit "移植"到新基底 |
| `git log -p --follow <file>` | 冲突时**最有用**的命令，看清这个文件在两边各自怎么演进的 |

### 5. 方案 C 的"渐进式落地"

不用专门抽时间做一次大重构。而是**每次新需求都问一次"能不能不碰已有文件"**：

- 想加新代理组？→ 在 src/proxy_groups.ts **末尾** push，不修改已有项
- 想加新规则？→ 在 src/rules.ts 末尾追加，不重排已有顺序
- 想加版本注入？→ **真的可以挪到构建期**：让 build.mjs 注入版本号到生成的 convert.js 里，**main.ts 不动**。这次同步就是顺路重构的好机会
- 想加新常量？→ 在 src/constants.ts 末尾追加，不动已有常量值

**一年下来，你的主干文件会和 upstream 主干文件"形状"高度一致，merge 永远是小冲突。**

| **B 补丁目录** | **有价值，但别做成「唯一真相」**。适合把「相对上游的差异」固化成可审计清单；长期维护成本高于纯 SOP。 | 差异点稳定、想可视化冲突 |
| **C 解耦重构** | **方向正确，但本次同步不要硬做**。自定义已经嵌进 `proxy_groups` / `rules` / `constants` / `main`，一次大拆风险高、回滚成本大。 | 下次或同步稳定后逐步做 |

**不推荐作为主方案的：**

- **纯 `git merge upstream/main` + 人工解 7 个冲突**：可行，但可审计性差，下次上游再改同一批文件还会再痛一次。
- **整仓 submodule / subtree 挂上游**：对这种「源码被深度改写」的 fork 几乎帮不上忙，反而多一层复杂度。
- **`merge -X ours/theirs` 一刀切**：会丢掉 Tailscale 或丢掉你的 AI/Adobe/Autodesk 逻辑，不符合「保住全部自定义 + 吸收有价值上游改动」的目标。

**为什么不是「只做 C」？**  
上游官方 `HOW_TO_CUSTOMISE.md` 本身就鼓励在 `src/rule_providers.ts`、`src/proxy_groups.ts`、`src/rules.ts`、`src/constants.ts` 里直接改。你的自定义（Must* 强制链、AI 组、Adobe/Autodesk）正是这类扩展，和上游设计一致。彻底解耦（独立模块 / 配置驱动）是「更好架构」，但不是「这次同步的最低风险路径」。长期可以朝「少改上游已有结构、多新增独立文件」演进，但本次应先安全追上 v2.7.0。

## 二、这次 v2.5.5 → v2.7.0 的最优执行步骤

核心原则：**以干净的上游 v2.7.0 为底，把「你的自定义」当成可复现的补丁重放上去**，而不是在「你的 main + 上游 main」的混合历史上硬 merge。

### 阶段 0：冻结与备份（必做）

1. 确认本地 `main` 干净、已推送到 origin。  
2. 打一个备份分支/tag，例如：  
   `git branch backup/pre-sync-v2.5.16`  
   `git tag backup-v2.5.16`  
3. `git fetch upstream`，确认 `upstream/main` 指向 v2.7.0（`e88deb8` 一带）。

### 阶段 1：导出「自定义清单」（强烈建议先做）

在**当前 main（v2.5.16）**上，相对基线算出差异，而不是相对最新上游：

```bash
# 基线：上游 v2.5.5
git fetch upstream
BASE=$(git rev-parse ca977f0)   # 或 upstream 的 v2.5.5 tag 对应 commit

# 只看源码与配置相关（排除 _fork、icons、ruleset 等纯新增可后处理）
git diff $BASE...HEAD -- src/ package.json package-lock.json \
  .github/workflows/release.yaml scripts/ > /tmp/custom-vs-base.diff
```

同时用文字清单（建议放进 `_fork/CUSTOM_DELTA.md`）按文件归类，例如：

| 文件 | 自定义点 | 与上游 v2.7 可能冲突点 |
|------|----------|------------------------|
| `src/rule_providers.ts` | MustDirect/MustProxy/MustReject/MyDirectCDN/Adobe/Autodesk | 通常无冲突（你已验证） |
| `src/proxy_groups.ts` | AI服务 / AI故障转移 / ADOBE / AUTODESK | 上游删 SSH、加 Tailscale、可能改分组结构 |
| `src/rules.ts` | Must* 强制链、Adobe/Autodesk 优先级、MyDirectCDN | 上游改成 `baseRules` 数组写法 |
| `src/constants.ts` | AI_FALLBACK / ADOBE / AUTODESK 等 | 上游可能增删组名 |
| `src/main.ts` | `x-override-rules` 元信息 | 可能有结构变动 |
| `src/node_parser.ts` | （若有自定义） | 上游 Tailscale 相关解析 |
| `src/dns.ts` | （若未改可整收上游） | 上游大改 fake-ip-filter |

**纯新增**（`_fork/`、`ruleset/Must*.list`、`icons/`、`scripts/sync-autodesk-list.sh`）在后续步骤里直接拷贝即可，几乎不产生冲突。

### 阶段 2：以 v2.7.0 为底建同步分支

```bash
git checkout -b sync/upstream-v2.7.0 upstream/main   # 或 v2.7.0 tag
```

此时工作树 = 干净上游。再把纯新增文件拷进来（不依赖 cherry-pick）：

```bash
git checkout main -- _fork/ ruleset/MustDirect.list ruleset/MustProxy.list \
  ruleset/MustReject.list ruleset/MyDirectCDN.list ruleset/Autodesk.list \
  icons/Adobe.png icons/Autodesk.png scripts/sync-autodesk-list.sh
# 以及你改过的 CI/脚本（若与上游不冲突）
git checkout main -- .github/workflows/release.yaml scripts/build.mjs .husky/ 2>/dev/null || true
```

### 阶段 3：重放「逻辑自定义」（推荐：按文件语义手工/半自动，而不是整段 50 个 commit cherry-pick）

你的 50 个 commit 是时间线历史，不一定适合逐个 cherry-pick（中间可能有试验、回滚、重命名）。更稳妥的是：

1. **对每个冲突高发文件**，用三路对比：  
   - 基线（v2.5.5）  
   - 你的最终版（main）  
   - 上游最终版（v2.7.0）  
2. 在 v2.7.0 文件上**重新实现**你的语义，而不是机械选「ours/theirs」。

建议顺序（依赖从少到多）：

1. `src/constants.ts` — 先加组名常量，后面才有得引用。  
2. `src/types.ts` — 类型扩展。  
3. `src/rule_providers.ts` — 通常可整段合入你的 provider 定义。  
4. `src/proxy_groups.ts` — **关键冲突点**：  
   - 保留上游：Tailscale 相关分组、删除 SSH、删除「低倍率」等。  
   - 保留你的：AI服务 / AI故障转移 / ADOBE / AUTODESK，以及 AI 组对国家分组的引用。  
   - 做法：以上游当前 `buildProxyGroups` 结构为骨架，把你的组按语义插回合适位置。  
5. `src/rules.ts` — **关键冲突点**：  
   - 上游已是 `baseRules` 数组写法，你应以**上游数组为底**，把 MustDirect/MustProxy/MustReject、Adobe/Autodesk、MyDirectCDN 等按**优先级顺序**插进去（强制链通常靠前）。  
6. `src/main.ts` — 只保留 `x-override-rules` 注入等差异，其余跟上游。  
7. `src/node_parser.ts` / `src/dns.ts` — 若你几乎没改，直接用上游；若有改，用同样三路对比。  
8. `package.json` / `package-lock.json` — 版本号、脚本钩子以你的发布流程为准，依赖版本尽量跟上游对齐后 `npm install` 重生 lock。

**冲突时如何判断保留哪边？**

- **语义优先，不文件优先**：问「这条改动解决的是谁的问题？」  
  - Tailscale 节点解析/分组/TUN 排除 → 上游  
  - Must* 强制直连/代理/拒绝、Adobe/Autodesk 分流、AI 故障转移 → 你的  
  - SSH 组、低倍率组被上游删除 → 接受上游（除非你明确还在用）  
- **结构优先跟上游**：例如 `rules.ts` 已改成 `baseRules`，你就不要坚持旧写法再 merge，而是把旧语义搬进新结构。  
- **不确定时**：先保留两边逻辑到注释里，本地 `npm run artifacts` 构建 + 用测试订阅验证，再删注释。

### 阶段 4：验证与发布

1. `npm install && npm run format && npm run lint:fix && npm run artifacts`  
2. 用真实订阅跑一遍 JS 覆写，检查：  
   - Must* 规则顺序与命中  
   - AI / Adobe / Autodesk 组存在且策略正确  
   - Tailscale 相关组与规则出现（若订阅里有相关节点）  
   - DNS / TUN 行为符合预期  
3. 更新 `_fork/STATUS`、`CHANGELOG`（你的记录体系），提交。  
4. 按你现有 `src-vX.Y.Z` tag + Actions 流程发版（版本号建议：同步后可标 `v2.7.0-fork.1` 或继续你的 `v2.5.x` 递增策略，但建议在文档里写清「基于上游 v2.7.0」）。

### 阶段 5：把过程固化进 A（SOP）

把上述步骤写成 `_fork/SOP_UPSTREAM_SYNC.md`，固定模板包括：

- 基线 commit / 目标上游 tag  
- 自定义清单路径  
- 文件处理顺序  
- 验证清单  
- 回滚分支名  

这样下次从 v2.7.0 → v2.8.x 时，只是「重复同一套剧本」。

## 三、方案 B 要不要上、怎么上才不贵

**轻量 B 有价值，重量级「补丁即真相」不推荐。**

建议做法：

1. 在 `_fork/patches/` 或 `custom-delta/` 下放**文档化的 diff 快照**（相对「某次成功同步后的上游基线」），用于审计，而不是每次 `git apply` 的唯一入口。

3. **不要**维护一长串与源码双轨同步的 `.patch` 文件——源码一改，patch 就失效，维护成本会高于直接三路合并。

若未来自定义稳定、且上游改动频繁，再考虑把「可机械应用的片段」（例如整段 rule-provider 对象、整段 proxy group 定义）抽成独立文件，用脚本合并进上游结构——那就是向 C 过渡。

## 四、关于 rule-provider 用 `@main` 拉 `.list`

这是你们设计里很聪明的一点：**规则数据与脚本发版解耦**。要注意的风险与对策如下。

| 风险 | 说明 | 建议 |
|------|------|------|
| **不可复现** | 同一 `convert.min.js` 版本，客户端下次拉到的 `.list` 可能不同 | 对关键规则集（Must*）在发版说明里记录「规则集大致状态」；需要严格复现时临时改 URL 为 `@某 commit` 或 `@某 tag` |
| **CDN 缓存** | jsDelivr 等对 `@main` 有缓存，改 list 后可能延迟生效 | 已知现象；紧急时可换 raw.githubusercontent.com 或带 commit 的 URL；或接受「最多延迟数小时」 |
| **误改 main** | 错误 list 推到 main 会立刻影响所有用 `@main` 的客户端 | `_fork` SOP 要求改 list 走 PR/自检；重要 list 可考虑 `ruleset/` 与 CI 简单校验（空文件、明显坏行） |
| **与脚本逻辑不匹配** | 脚本里引用了 provider 名，但 list 被删/改名 | 发版前 checklist：provider 名 ↔ 文件名一致 |

**是否值得给 `.list` 也做版本化？**

- **日常：保持 `@main` 动态**——符合「改规则不用发版」的目标，省力。  
- **需要冻结时**（例如对外分享「某次稳定配置」、或排查「上周还能用这周不行」）：  
  - 短期：客户端 URL 改成 `@commit` / `@tag`；  
  - 中期：可选 `ruleset` 打 `rules-vYYYYMMDD` tag，文档说明「脚本版」与「规则版」可独立引用。  

一般个人自用 fork **不必**强制规则集跟脚本同版本号；在 `_fork/STATUS` 里记一句「当前规则集以 main 为准」即可。

## 五、长期维护的最佳实践（个人 Fork）

结合上游官方自定义指南与你的现状，可持续策略可以概括为：

### 1. 扩展优先于修改（朝 C 渐进）

- **优先**：新增 `ruleset/*.list`、在 `rule_providers.ts` 增加 provider、在 `proxy_groups` / `rules` **追加**组与规则、在 `constants` **追加**常量。  
- **谨慎**：改上游已有函数的控制流、重排整份 `baseRules`、改 node 解析主路径。  
- **目标形态**：`src/` 里与上游的 diff 尽量是「插入块」，而不是「大段替换」。这样未来 `git merge` 或「以新版本为底重放」都会更轻松。

### 2. 单一上游跟踪分支策略

- `main`：你的对外稳定线（自定义 + 已同步的上游）。  
- `upstream-tracking` 或仅用 `upstream/main` remote：只跟上游，不掺自定义。  
- 每次同步：从 `upstream/main`（或 tag）拉出 `sync/vX.Y.Z`，重放自定义，验证后合回 `main`。  

避免长期「main 上反复 merge upstream」导致历史难以阅读；merge 可以，但「重放语义」比「保留 merge 拓扑」更重要。

### 3. 自定义必须可枚举

`_fork/CUSTOM_DELTA.md`（或等价 ADR）维护一张表：文件 → 自定义意图 → 依赖的上游结构。同步时只对照这张表，而不是凭记忆解冲突。

### 4. 发版与规则集分工保持现状

- 源码/逻辑 → tag + dist + Release。  
- 规则数据 → `@main` 动态。  
- 文档在 README/`_fork` 里写清楚，避免使用者以为「升脚本版本才会更新 MustDirect」。

### 5. 上游大改时的决策框架

每次同步前花 15 分钟读上游 CHANGELOG / commit（本次重点：Tailscale、去 SSH、rules 重写、dns 重写）：

- **吸收**：安全修复、新协议/新场景支持（如 Tailscale）、明显的结构改进。  
- **可丢**：你不用的分组（SSH、低倍率）。  
- **必须重做**：与你自定义同一文件的重构（如 `baseRules`）——接受「搬语义」而不是「保 diff」。

### 6. 何时认真做 C

满足任一条件再投入解耦重构更划算：

- 上游连续 2～3 个大版本都在改你改过的同一批文件，且每次同步超过半天；  
- 你希望把「AI / Adobe / 强制链」做成可开关的参数或独立包，方便多环境复用；  
- 有第二人一起维护 fork。  

在此之前，**A + 轻量清单 + 按语义重放**已经是个人 fork 里性价比最高的组合。

## 二、本次 v2.5.5 → v2.7.0 同步的最优执行步骤

基于我对上游 11 个 commit 的逐条分析，这次同步的核心冲突**不是逻辑冲突，而是结构性冲突**：

- `package.json/package-lock.json`：常规依赖更新

### 推荐策略：**"干净基底 + 结构化重放"**，而非直接 merge

直接 `git merge upstream/main` 会让您在 7 个文件的冲突中做"二选一"的微观决策，极易出错。更好的方式是：**先完全接受上游 v2.7.0，再系统性地把自定义重放回去**。

#### 步骤 1：预演与清单梳理


## 三、@main 动态拉取 .list 的风险评估

您的直觉是对的，这个设计**确实引入了风险**：

| 风险 | 说明 | 严重程度 |
|------|------|----------|
| **版本不可复现** | 用户用 `src-v2.7.0` 的 `convert.min.js`，但 `ruleset/*.list` 是 @main 实时拉取的。今天和明天的规则集可能不同，导致"同样的 release，行为不一致" | 🔴 **高** |
| **CDN 缓存延迟** | jsdelivr 对 `@main` 有缓存（通常 5-60 分钟），改了 `.list` 后不会立即全局生效 | 🟡 **中** |
| **回滚困难** | 如果 `.list` 的改动导致问题，无法通过回滚 `src-*` tag 来回滚规则数据 | 🔴 **高** |
| **意外破坏** | 直接推 main 改 `.list` 没有 review 流程，容易误操作 | 🟡 **中** |

### 建议

**短期（保持现状）**：在 `_fork/ADR/` 中增加一条决策记录，明确接受这些风险，并约定：
- `.list` 的改动必须是**追加性**的（只增不减），避免破坏性变更
- 重大规则调整时，通过 `src-*` tag 发版，在 `convert.min.js` 中引用带版本的 rule-provider URL

**中期（推荐改进）**：为 `.list` 引入轻量版本化。两种做法：

**做法 A（推荐）：在 dist 分支中同步发布 .list**
```yaml
# release.yaml 中增加一步：
- name: Sync ruleset to dist branch
  run: |
    git checkout dist
    cp -r ruleset/ dist/ruleset/
    git add dist/ruleset/
    git commit -m "sync ruleset for $(git describe --tags)"
    git push origin dist
```
然后 rule-provider URL 改为：
```
https://cdn.jsdelivr.net/gh/LeiD215/override-rules@src-v2.7.0/ruleset/MustDirect.list
```
这样 `.list` 也随 `src-*` tag 版本化了。

**做法 B（更轻量）**：不改发布流程，但在 `src/main.ts` 中把 rule-provider 的 URL 模板改为可配置：
```typescript
const RULESET_BASE_URL = config["x-ruleset-branch"] 
  ? `https://cdn.jsdelivr.net/gh/LeiD215/override-rules@${config["x-ruleset-branch"]}`
  : `https://cdn.jsdelivr.net/gh/LeiD215/override-rules@main`;
```
让用户可以选择用 `@main`（实时）或具体 tag（稳定）。

## 四、长期维护的最佳实践

您的最后一个问题其实已经触及了核心：**个人 Fork 跟随上游最可持续的模式是什么？**

答案是：**"少改上游源码，多通过扩展点注入"**。

### 当前问题诊断

您现在的自定义模式是**"侵入式修改"**：
- `proxy_groups.ts`：直接在上游的代理组数组中插入新组
- `rules.ts`：直接在上游的规则数组中插入新规则
- `constants.ts`：直接在上游的常量对象中新增键

这意味着上游每改一次这些文件的结构，您就要人工同步一次。

### 向方案 C 渐进演进的路线图

**阶段 1（本次同步后立即做）**：
- 把 `src/rule_providers.ts` 的自定义逻辑整理成**纯数据驱动**：用一个 `CUSTOM_RULE_PROVIDERS` 数组定义所有自定义 provider，然后循环注册
- 这样下次上游改 `rule_providers.ts` 的结构时，您只需要改循环逻辑，不需要逐个改 provider 定义

**阶段 2（下次同步前）**：
- 在 `src/proxy_groups.ts` 中引入**"扩展点"**：上游的 `buildProxyGroups` 返回的数组末尾加一个 `...customProxyGroups` 展开
- 自定义代理组全部放到 `src/custom/proxy_groups.ts` 中
- 这样 `src/proxy_groups.ts` 本身可以尽量贴近上游

**阶段 3（未来）**：
- 推动上游（或自己 fork 后重构）把 `buildRules`、`buildProxyGroups` 改为接受**"扩展配置"**参数
- 最终目标是：自定义完全通过 JSON/YAML 配置文件驱动，不需要改任何 `.ts` 文件

### 每次同步的标准流程（SOP）

把以下内容写入 `_fork/SOP-SYNC.md`：

```markdown
# 上游同步 SOP

## 前置条件
- upstream remote 已配置且可 fetch
- 本地工作区干净

## 步骤
1. `git fetch upstream`
2. 查看上游 release notes，记录需要吸收的功能
3. 创建同步分支：`git checkout -b sync-vX.Y.Z upstream/<tag>`
4. 应用零冲突 patch：`git checkout main -- ruleset/ _fork/ icons/ scripts/sync-autodesk-list.sh`
5. 尝试自动应用 custom patches：`./scripts/apply-patches.sh`
6. 对报错的 patch，采用"接受上游 + 重放自定义"策略手动处理
7. 构建验证：`npm run artifacts`
8. 提交、合并、打 tag、推送
9. 更新 _fork/CHANGELOG.md 和 _fork/STATUS.md
```
